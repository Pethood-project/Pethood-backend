# Spec 003 — Verificación documental de usuarios (DNI + selfie)

**Estado:** BORRADOR — pendiente de acuerdo del equipo (extiende HU-2.3 más allá del documento fuente)
**Sprint:** — · **Responsable:** ncorrea-13 · **Última actualización:** 2026-08-24

## 1. Objetivo

Que el administrador pueda verificar la identidad real de un usuario viendo una foto de su DNI y una selfie antes de aprobarlo (HU-2.3). Hoy la verificación solo comprueba que `dni` y `telefono` estén cargados — no hay evidencia documental que respalde la decisión.

> Advertencia: esta spec va más allá del relevamiento original. REQUISITOS.md:101 dice literalmente "verificación de DNI y teléfono". Si el equipo aprueba, sumar la ambigüedad a REQUISITOS.md §10 y actualizar MODELO_DATOS.md en el mismo PR.

## 2. Alcance

- **Incluye:** subida de DNI + selfie por el dueño de la cuenta (app mobile, cámara o galería); visualización de esos documentos por el admin previo a verificar; exigencia de documentación completa como condición de verificación.
- **NO incluye:** comparación facial automática / biometría (post-MVP); verificación documental de refugios (personería, habilitaciones — spec aparte si se pide); re-verificación de usuarios ya verificados; flujo de rechazo con estados intermedios: si los documentos salen ilegibles, el usuario vuelve a subirlos reemplazando los anteriores (v1).

## 3. Entidades involucradas

Sin clase nueva (decisión: ponytail — dos columnas alcanzan; una entidad `Verificacion_Usuario` con historial solo tiene sentido si aparece el flujo de rechazo/aprobación con estados, ver §9):

```prisma
model Usuario {
  // ...existente...
  dniImagenUrl String? @map("usuario_dni_imagen_url")
  selfieUrl    String? @map("usuario_selfie_url")
}
```

Migración: `npx prisma migrate dev --name verifica-documental-usuarios`. Ambas nullable: cuentas Google ya existentes no tienen documentos hasta que los suban.

Storage: mismas reglas que la foto de perfil (`shared/storage.ts`) — R2 si está habilitado, disco local si no.

## 4. API (contrato backend)

| Método | Ruta | Auth | Descripción |
|---|---|---|---|
| POST | /api/v1/usuarios/me/documentos | JWT (dueño) | multipart: sube/reemplaza DNI y/o selfie |
| GET | /api/v1/admin/usuarios/:id | rol Administrador | Detalle del usuario para el panel: datos + URLs firmadas/planas de dniImagenUrl y selfieUrl |

El endpoint admin es nuevo (el listado sigue devolviendo filas livianas sin imágenes). El de subida extiende el patrón de `PATCH /usuarios/me` (multipart con campo `imagen`).

### Ejemplos

```
POST /usuarios/me/documentos        ← multipart
  dni_imagen: archivo (jpg/png/webp, <=5MB)
  selfie:     archivo (jpg/png/webp, <=5MB)
→ 200 { "mensaje": "...", "documentos": { "dniImagenUrl": "...", "selfieUrl": "..." } }

GET /admin/usuarios/:id
→ 200 { usuario..., "documentos": { "dniImagenUrl": "...", "selfieUrl": "..." } }
```

Errores: `400 VALIDACION` (archivo faltante/pesado/formato — reutiliza mensajes GUI-0.1.6); `403 NO_AUTORIZADO` (subir documentos de otro usuario); `404 USUARIO_NO_ENCONTRADO`.

## 5. Pantallas (frontend)

**App mobile (`apps/mobile`)**
- Sección "Verificación" dentro del perfil (HU-1.3/1.5): estado actual ("Verificado" / "Pendiente de revisión" / "Falta subir documentación"), botones para capturar/subir DNI y selfie, vista previa antes de confirmar.
- Toast voseo al subir (GUI-0.1.1) y aviso de que la revisión es manual.

**Panel web-admin (`apps/web-admin`)**
- Modal previo a verificar (mismo patrón que el detalle de refugio de spec 002): datos del usuario + las dos imágenes a tamaño legible + DNI/teléfono como texto para cotejar.
- El botón "Verificar" del listado abre este modal en vez de confirmar directo.
- Si falta documentación, el botón queda deshabilitado con tooltip explicativo (además del 409 del backend).

## 6. Reglas de negocio y validaciones

1. Imágenes: jpg/png/webp, max 5MB cada una (regla transversal #5, validación compartida `shared/validation`). Backend es fuente de verdad; mobile valida antes por UX.
2. Subir reemplaza el documento anterior (update de la URL); solo el dueño puede subir sus documentos.
3. Verificación exige ahora cuatro cosas: `dni`, `telefono`, `dniImagenUrl`, `selfieUrl`. Si falta cualquiera → `409 FALTA_DOCUMENTACION` (reemplaza/enriquece el actual `DATOS_INCOMPLETOS`; acordar código final con el frontend).
4. La subida no cambia el estado del usuario ni marca nada: solo deja evidencia lista. Quien decide es el admin con PATCH /verificar (transición existente de spec 002).
5. Compresión asíncrona de imágenes en middleware antes de persistir (regla transversal #4).
6. Privacidad: las URLs de documentos solo viajan al dueño (en su perfil) y a admins. Nunca en listados públicos ni feed.
7. Auditoría: la subida setea fechaModificacion; la verificación ya escribe LogAuditoria (spec 002 regla 7). En la entrada de auditoría de verificación queda registrado que había documentación (no las URLs).
8. Selfie desde cámara nativa en mobile cuando sea posible (mismo espíritu anti-fraude que HU-9.1), pero v1 no lo bloquea a nivel backend: el backend no puede asumir origen confiable de ninguna imagen (regla transversal #9).

## 7. Criterios de aceptación

- [ ] Given usuario sin documentos, When sube DNI y selfie válidos, Then 200 y quedan visibles en su perfil.
- [ ] Given imagen de 8MB, When sube, Then 400 VALIDACION con mensaje GUI-0.1.6.
- [ ] Given usuario autenticado distinto, When intenta subir documentos de otro, Then 403.
- [ ] Given usuario con DNI+teléfono pero sin documentos, When admin verifica, Then 409 FALTA_DOCUMENTACION.
- [ ] Given usuario con todo completo, When admin abre el modal de verificación, Then ve ambas imágenes y puede verificar; queda registro en LogAuditoria.
- [ ] Given adoptante llamando GET /admin/usuarios/:id, Then 403 ROL_NO_AUTORIZADO.
- [ ] Given usuario verificado, When sube documentos nuevos, Then se reemplazan pero su estado no cambia (no hay des-verificación accidental).

## 8. Casos borde y errores

- Cuenta Google sin DNI cargado: puede subir documentos igual; el DNI numérico sigue pudiendo completarse desde perfil (o parsearse del documento por el admin manualmente — decisión UI, no backend).
- Subida con conexión perdida: reintento idempotente (reemplaza lo anterior, no duplica filas — es update de columnas).
- Usuario suspendido/baja: conserva sus documentos; no puede subir nuevos mientras no esté Activo (coherente con bloqueo general de cuentas no activas).
- Refugio operador: misma mecánica (es un Usuario más).
- Borrado físico de imágenes viejas al reemplazar: v1 deja el archivo huérfano en storage (nota: limpieza futura por cron si crece).
